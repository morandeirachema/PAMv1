the login-flow enumeration trap a naive design would hit is closed by minting a narrow, password-gated session scope before ever building a challenge. **Phase 126** closed the plan's sixth and final item, added after approval on a direct ask: selectable portal color themes — every hardcoded color became a CSS custom property, two new dark palettes (amber, slate) sit alongside the existing green as `[data-theme]` overrides, and **F2** cycles between them client-only, no new store table, route or audit event — completing the Wallix-weighted plan's full run. **Phase 128** then returned to the original CyberArk/Wallix gap-research backlog's remaining item: authenticated post-login account discovery — a fixed, read-only enumeration command run over a target's own vaulted credential, cross-referenced against every credential pamv1 already vaults for that target, so a login-capable account the host has but pamv1 doesn't track ("unmanaged") is surfaced as a finding, CyberArk DNA-style. **Phase 129** extended Zero Standing Privilege (Phase 22, SSH-only until now) to PostgreSQL: a `db_zsp` credential provisions a fresh, randomly-named role via the target's separately vaulted provisioner credential and drops it when the session ends, so no standing database secret exists for the connecting identity at all — proven against a real Postgres wire-protocol exchange. Two exclusions decided *before* writing code, not discovered after: RDP has no equivalent (Guacamole's own documentation confirms no certificate-based RDP auth parameter exists, a permanent protocol limitation), and SQL Server is deferred (`internal/tds` has no client-side response-token reader yet). **Phase 131** added an optional command allow-list (`PAM_COMMAND_ALLOW_FILE`): `cmdguard.Guard` gained an `Allowed(cmd)` method reading the same compiled pattern set `Blocked` already does, so an allow-list is just a second Guard value used the other way round, wired at every existing command-control call site — deny always wins when both would match. **Phase 133** closed the batch's second item: a pluggable `internal/posture` webhook re-checks live device posture on every connect and every authenticated call (a new gate in `gates.go` plus a matching `authz` check, both break-glass exempt), and an optional `PAM_DEVICE_HEADER` binds a principal to one reverse-proxy-injected client-certificate fingerprint — honestly scoped to the REST surface only, since the three raw SSH/PostgreSQL/SQL Server proxies have no HTTP layer for a header to travel on. Neither check can reach a `RoleAgent` identity: the broker's tools bypass `admit()` entirely and never authenticate through `authz`. **Phase 135** closed the batch's third item, DoubleLock: a named person's password, independent of RBAC, additionally required to reveal or check out a credential — even a compromised admin account can't read it alone, and can't strip the protection without that same password either. The plan's original AAD-mixing-on-the-existing-vault mechanism didn't survive contact with `-rotate-kek`'s exhaustive KEK re-wrap, which has no way to obtain a password mid-rotation — resolved by keeping the DoubleLock ciphertext entirely outside the KEK (a second, independent AES-256-GCM encryption keyed directly by PBKDF2(password)), so `-rotate-kek` needed zero changes. **Phase 137** closed the batch's fourth item, two independent pieces bundled together: magic-link access-request approval, an `ApprovalInvite` that near-structurally copies Phase 116's session-share invite but needs no separate approval step of its own — creating one already requires `CapApprove`, so the invite is the delegation — with redemption split into a safe preview `GET` and a single-use decision `POST` fired only on an explicit click, deliberately unlike `share.html`'s auto-redeem, since a decision is higher-stakes than joining a session; and session watermarking, a client-side overlay for RDP/VNC and a one-time `Hub.Publish` banner for text/database sessions. Tracing the self-approval attack surface by hand (not a failing test) found that the redemption path's synthetic actor alone didn't stop a requester minting an invite to their own inbox — closed by a second four-eyes check at invite creation. **Phase 139** closed the batch's fifth item, and the first to change a real, load-bearing invariant rather than add a gate alongside the existing ones: `auth.CanConnectTarget` admitted any admin unconditionally, so a safe marked `Personal` (Delinea's personal folders) means nothing unless that stops. The bypass is now conditional on a new, narrow `CapUnlimitedVaultAccess` capability, deliberately absent from the built-in admin role. Building it surfaced a second side door the plan text hadn't named: `canManageSafe` let any `manage_targets` holder add themselves to any safe's roster, personal or not — closed the same way, with a bootstrap fix (`createSafe` requires and seeds an `owner`) so a personal safe is never created unmanageable. **Phase 141** closed the batch's sixth item: a client-initiated `ssh -L` forward is admitted only to the connected target's own host — any port, since the target's own configured port is its SSH port, not the service the operator actually wants — closing what would otherwise be an SSRF pivot into the target's network. The real design question the plan text didn't answer was what "same host" means: `localhost`/`127.0.0.1`/`::1` count as the target too, since the forward dials out through the already-authenticated upstream connection, resolved from there. Three refusals nothing automatically covers were found by asking what a bare channel-loop branch inherits from `handleSession` (nothing): observer sessions, mandatory live supervision and required recording all refuse forwarding outright rather than silently admitting an uncovered data path. **Phase 143** closed the batch's seventh item, ICAP-based AV/DLP scanning of SFTP transfers — and the plan's own assumption that this could "fail closed like the byte cap" didn't survive reading the capture code: a whole-object scan needs a complete file, which only exists once a transfer has already reached its destination through the existing per-packet relay. Rather than force a store-and-forward rearchitecture the proxy doesn't have, this shipped as an honest scope cut — **detection, not prevention** — with a new minimal `internal/icap` RFC 3507 RESPMOD client, a flagged or failed scan audited loudly (`sftp.icap_flagged`/`sftp.icap_scan_failed`) without ever blocking the transfer, and a dedicated end-to-end test proving an unreachable scanner still lets the file through exactly as documented. **Phase 145** closed the batch's eighth item, generic file-attachment secrets — mechanically nothing new, the same `vault.Encrypt`/`Decrypt` pathway every secret type already uses, capped at `PAM_CREDENTIAL_FILE_MAX_KB` before it is ever encrypted. The real story is a near-miss the plan's own stated fix walked past: stripping `secret_enc` from `ListCredentials` (its own doc comment said the field is `json:"-"` and "gets materially worse the moment attachments exist") passed a store-layer contract test written to prove it worked, then broke the PostgreSQL session proxy's JIT credential injection in production — caught only because the full test suite includes a real in-process upstream. `dbproxy.go`'s `lookupTargetCred` deliberately lists first and decrypts from the result later, by design, so every authorization gate can run before any plaintext exists; a repo-wide grep found nine such callers, not the two or three a narrower search inside `internal/api` alone would have suggested. Resolved by leaving `ListCredentials` untouched and adding a new, separate `ListCredentialsMeta` for the four callers actually verified to never touch the secret. **Phase 147** closed the batch's ninth item, browser-extension password autofill — a real Manifest V3 extension calling the *existing* reveal route with a new narrow session scope, `auth.SessionScopeExtension`, refused everywhere except that one endpoint. Unlike the RDP/VNC viewer scope (a blanket refusal with no exceptions anywhere), this one needed exactly one — built by extracting the shared REST authorization checklist into `authzCore(cap, allowExtension, next)` once, rather than risking a second, driftable copy of it. The minted token inherits the minting user's own role and capabilities, so it grants nothing beyond what that user could already reach through the normal reveal path. Not interactively verified against a real browser in this environment (no GUI browser available) — a documented gap, not a silent one, in the same honest spirit as Phase 129's unverified RDP/guacd finding. **Phase 149** opened the batch's back half with SCIM 2.0 user provisioning — StrongDM's push-based IdP lifecycle, complementing pamv1's existing pull-only `POST /api/identity/reconcile`: a new `/scim/v2/Users` surface, authenticated by a non-human `ScimKey` bearer identity (the same shape `AgentKey`/`AppKey` already use), full create/read/replace/patch/delete against `store.User`, which gains two fields — `ExternalID` (the IdP's own correlation key) and `Active`, SCIM's deprovisioning switch. Making `Active` mean something is the actual point: `auth.Resolver.Resolve()` now refuses a deactivated user's local token outright, proven end to end against a real token before and after a real deactivating PATCH call, not asserted at the store layer alone. `CreateUser` in both backends now ignores whatever `Active` a caller's input struct holds and always creates an active user — a bare `bool` cannot distinguish "wants inactive" from "never heard of the field," and the second case must never silently create a deactivated account; this caught a real regression in `internal/auth`'s own pre-existing test fixtures, which build `store.User` values directly rather than through `CreateUser` and so needed the same explicit fix. SCIM's own `DELETE` is a deliberate soft-delete (sets `Active=false`), diverging on purpose from `DELETE /api/users/{id}`'s existing hard-delete semantics, since SCIM's whole model depends on being able to reactivate. Every SCIM-provisioned user gets the fixed `RoleUser` floor — a SCIM key holds no capability set of its own to bound a requested role against, unlike a human caller of `POST /api/users`. Not interactively verified against a real IdP (no Okta/Azure AD/OneLogin account available); the wire-shape handling is close enough to matter regardless — PATCH honors both RFC 7644's path-based form and Azure AD's documented no-path variant. **Phase 151** closed the batch's Delinea finding — SAML 2.0 single sign-on for the IdPs that speak SAML but not OIDC (on-prem AD FS above all, plus SAML-only Okta/OneLogin/Entra applications): pamv1 as a Service Provider in the SP-initiated Web Browser SSO profile, following `internal/oidc`'s exact wiring shape (`buildSAML` beside `buildOIDC`, the same hot-swap closure, the same `MatchedRoles` group→role mapper, the same portal landing) — and the second deliberate crypto-verification library exception after WebAuthn, reasoned through in ROADMAP.md: XML-DSig over canonicalized XML is precisely where the signature-wrapping vulnerability class lives, a different order of problem than OIDC's fixed-bytes JWT check, so the verification is delegated to `crewjam/saml`+`goxmldsig` and pamv1 keeps only the policy decisions (SP-initiated only, request ID bound to a browser cookie and consumed single-use from the existing OIDC-state store — no schema change — no IdP-initiated logins, no SLO). Proven against a **real in-process SAML IdP** in the test suite, signed and encrypted assertions alike, with tampered, stripped, wrong-audience, wrong-issuer, expired and signature-wrapped Responses refused; interop with a live ADFS/Okta tenant is not verified in this environment. **Phase 153** took on the batch's most architecturally different item — outbound-only endpoint agents, BeyondTrust's Jump Client: every earlier phase added a gate, a protocol or a store concept to pamv1's dial-out model, and this one inverts it for the endpoints pamv1 can never reach (NAT, CGNAT, no inbound rule — where a jump host doesn't help either, since the bastion still has to reach the target). A third binary, `cmd/pam-agent`, dials OUT to the existing `:2222` listener with its own bearer key, holds an RFC 4254 reverse tunnel, and the proxy opens streams back through it instead of dialing — the client half was free (x/crypto already implements `ssh -R`'s mechanism), the server half was the real work (pam-server used to discard every SSH global request; it now accepts exactly one `tcpip-forward` from an agent-class identity and refuses every channel that identity opens). Boundaries decided up front: the agent alone chooses the ONE local address it exposes, pins pam-server's host key or refuses to run, and can carry nothing toward pamv1; a bound target is tunnel-or-nothing, never a silent direct fallback; per replica, so an agent lists every replica. Proven with the real agent library against a real upstream sshd through the tunnel; a real NAT path is not verified here. **Phase 155** closed the batch's one cross-vendor-confirmed top finding — Kubernetes, which Teleport and StrongDM flagged independently and which was notably absent from pamv1's own connector-breadth gap list: a `kubernetes` target is a cluster's API server rather than a host, so there is no session to proxy and pamv1 brokers discrete, audited kubectl-shaped operations instead (`get`, `logs`, `apply`, `delete`), each one call with a just-in-time-injected service-account token, the canonical `kubectl …` line matched by the same command control that governs SSH, a `.k8s.log` transcript and an audit row carrying the cluster's own status. The client is hand-rolled (HTTPS + JSON, no `client-go`, no discovery walk — the caller names the API version, so one operation is one request and CRDs work immediately), and its security core is path safety: every value that becomes a URL segment is validated against Kubernetes' own naming rules first. Streaming verbs (`exec`/`attach`/`port-forward`) are a documented exclusion, not an oversight — auditing a multiplexed SPDY stream needs a parser this codebase has no precedent for. **Phase 157** closed the batch with its last item and its second outright go/no-go: Teleport's eBPF session recording cannot be reproduced by a proxy at all — an operator's shell runs in the TARGET's kernel, so a probe on the pamv1 host observes nothing of a brokered session, and the only pamv1 code that ever runs on a target (the Phase 153 agent) would need a process-tree correlation and a reporting path that phase deliberately refused. What shipped delivers the same stated outcome by the only mechanism available to a proxy: after an interactive session ends, pamv1 pulls the TARGET's own kernel audit records over the same vaulted credential on a fresh connection, filters them to that session's window, and stores a hash-chained artifact beside the recording — so an obfuscated `base64 -d | sh` or an unechoed command still leaves a structured record of what actually ran, with "the target could not tell us" reported as a finding rather than silence. **Phases 159 and 161 open a new batch, the first ever aimed at pamv1's own AI-agent broker rather than at its human-operator paths**: 159 made an agent identity stoppable — suspend, expire and a subject-keyed quarantine that covers the SPIFFE/SVID identities which have no local row to disable, checked at the front door and again when a parked call comes up for approval, failing closed on a store error; 161 made an agent's behaviour *visible*, which it had never been. Every brokered tool call was written to the primary trail as one action with the outcome buried in the detail text, so the SIEM export's Detection-Finding rule for a denial had never fired since Phase 27 and the behavioural risk engine had no agent action in any signal map at all — an agent could act at any rate, at any hour, against hosts it had never touched, and score zero. The action now carries the outcome, agents are scored (with one deliberate exemption: never for off-hours, since 03:00 says nothing about a machine), and a run is reconstructible — the declared run id the API had accepted since Phase 13 and written nowhere, declared client/model provenance, and the resume token's id joining a parked call to the moment its result was actually collected, which the hash chain had never recorded. **Phase 163** continued that batch into the policy engine itself, and found the batch's sharpest defect so far: a `not_in` block-list was satisfied by an ABSENT argument, so the guard an operator would naturally write to keep an agent away from a few targets' credentials was defeated by omitting the argument it guarded — the widest form of the call was the one form the rule could not stop. Every operator now requires presence, `present: true|false` expresses absence deliberately, and tool arguments are validated against the tool's own declared schema before policy sees them, so an undeclared, missing, mistyped or empty argument is refused rather than quietly becoming a wider request. **Phase 165** bounded how much data an agent can pull: the SSH exec primitive read remote output with no limit at all — the primitive behind the broker's `ssh_exec`, account discovery, rotation verification and the forensics pull, making a policy-allowed `cat` of a large file a memory-exhaustion vector against the PAM host — and a tool's result reached the agent uncapped. Both are bounded now, and `ssh_exec` finally writes the durable transcript every sibling path already wrote, which is what makes truncating the agent's copy honest rather than lossy. **Phase 167** added the volume control a rate limit cannot express — a cumulative per-agent call budget over a rolling 24 hours, counted from the audit trail itself so the number an operator reads and the number the gate enforces cannot drift. See the [ROADMAP](../ROADMAP.md) for the authoritative per-phase status and [EXTERNAL-INFRA-GAPS.md](EXTERNAL-INFRA-GAPS.md) for what remains.

## 1. Purpose

pamv1 is an open-source Privileged Access Management system. It stores privileged
credentials in a hardened vault, brokers access to Linux/Windows targets through a
proxy that injects those credentials just-in-time, and records who did what. It is
designed to fit IT and OT (industrial) environments and to support NIS2 obligations.

> ⚠️ Educational project — see the note at the top of the [README](../README.md).

## 3a. Roles (RBAC)

Four profiles, enforced identically by the API and the proxy through a shared
capability matrix:

| Role | Can | Cannot |
|---|---|---|
| **admin** | everything: manage targets/credentials/users, reveal secrets, connect, read audit | — |
| **user** | connect to targets through the proxy, read the inventory | manage, reveal, read audit |
| **auditor** | read the inventory and the audit trail | manage, reveal, connect |
| **approver** | read inventory + audit, approve/deny access requests (`/api/access-requests`, 4-eyes) | manage, reveal, connect |

Beyond the four built-in roles, admins define **custom permission profiles** — named
capability sets assignable to users (Phase 12) — and AI agents authenticate as a
non-human `agent` role that can only call broker tools (Phase 13).

Identity is a per-user access token, the bootstrap admin key, the break-glass key,
or a directory login (AD/LDAP, Entra ID, OIDC — Phase 3b; SAML — Phase 151). A directory user in
several mapped groups carries **all** the roles they map to and is granted the
**union** of those capabilities (not just the single highest role).

## 4. Key flows

### 4.1 Vault a credential (control plane)

```mermaid
sequenceDiagram
    actor Admin
    participant API
    participant Vault
    participant DB
    Admin->>API: POST /api/credentials (secret)
    API->>Vault: Encrypt(secret, AAD=target:ID)
    Vault-->>API: v2:ciphertext
    API->>DB: store ciphertext only
    API->>DB: append audit (credential.create)
    API-->>Admin: 201 (no secret echoed)
```

### 4.2 Access a target via the proxy with JIT injection

```mermaid
sequenceDiagram
    actor Operator
    participant Proxy
    participant Vault
    participant Target as Linux target
    Operator->>Proxy: ssh target@pam (auth: API key*)
    Proxy->>Vault: decrypt credential (just-in-time)
    Vault-->>Proxy: plaintext (in memory only)
    Proxy->>Target: SSH auth as target user (injected)
    Proxy->>Proxy: record session (asciicast + SHA-256)
    Target-->>Operator: proxied I/O (secret never shown)
    Proxy->>Proxy: append audit (session.start/record/end)
```

`*` The operator authenticates with a PAM token (a per-user token, the bootstrap
API key, or a directory/session token); MFA and SSO shipped in Phase 3b.

## 5. Cross-cutting concerns

- **Confidentiality**: secrets encrypted at the application layer (AES-256-GCM) on top of a hardened DB; plaintext exists only transiently inside the proxy during a dial.
- **Attribution**: every sensitive action is an append-only audit event with an actor.
- **Availability / emergency**: break-glass path (Phase 1) → quorum + auto-expiry (Phase 6).
- **Deployability (IaC)**: Docker, docker-compose, Kubernetes manifests, Terraform module — no hand-applied infrastructure.
- **Compliance**: NIS2 Art. 21 mapping (README); IEC 62443 / Purdue positioning for OT (Phase 8).
